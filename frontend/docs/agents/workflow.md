# Workflow

## 작업 범위와 사용자 변경 보호

- 요청 범위는 사용자가 승인한 기능·문제 해결을 기준으로 판단함. 이를 완성하는 데 직접 필요한 코드·타입·테스트·문서 변경은 사용자가 파일명을 나열하지 않았어도 포함함. 무관한 기능이나 다른 저장소의 작업까지 확장하지 않음.
- 기존 사용자 변경은 보존함. 같은 파일에 사용자 변경이 있다는 이유만으로 작업을 중단하지 않음. 해당 변경을 덮어쓰거나 의도를 바꿔야 하고 기존 요청으로 승인 여부를 판단할 수 없을 때만 그 부분을 확인함.
- 사용자 변경을 임의로 수정·삭제·복구하지 않음. 사용자 변경의 커밋과 Git 이력 조작은 [git.md](git.md)를 따름.

## 자율 진행과 질문

- 승인된 구현 요청은 관련 조사·구현·검증·문서 반영까지 진행함. 계획이나 중간 결과만 제시하고 불필요하게 멈추지 않음. 리뷰·계획만 요청받은 경우에는 해당 범위를 유지함.
- 기존 코드와 문서로 판단 가능한 사항, 되돌릴 수 있는 일상적 구현 선택은 합리적인 기본값으로 진행하고 중요한 가정을 알림.
- 답변에 따라 제품 동작·권한·데이터 처리·작업 범위가 실질적으로 달라지며 기존 요청과 지침으로 결정할 수 없을 때만 질문함. 답변이 필요한 부분을 제외한 독립적인 작업은 계속함.
- 명시적 승인 요구는 유지함. 같은 범위에 이미 받은 승인을 다시 요구하지 않으며, 그 승인을 다른 대상·작업으로 확대하지 않음. 응답이 없다는 이유로 승인을 받은 것으로 간주하지 않음.
- 기술적 장애는 허용된 범위에서 해결을 시도함. 해결에 사용자 정보나 별도 권한이 필요하면 막힌 부분과 필요한 내용을 구체적으로 알리고, 가능한 나머지 작업을 진행함. 장애·미검증·완료 상태의 보고는 [testing.md](testing.md)를 따름.

## 구현 원칙

- 구현 전 관련 코드·테스트 또는 재현 방법을 확인함.
- 기능 변경과 대규모 리팩터링을 섞지 않음.
- 기존 코드 재사용이 가능하면 재사용함.
- YAGNI와 KISS를 우선함. 책임이 실제로 다를 때만 분리함.
- DRY는 코드 모양이 아닌 변경 이유 기준으로 판단함.
- SOLID는 실제 문제가 있을 때만 적용함.
- 미래 확장 예상만으로 계층·패턴을 추가하지 않음.
- 관련 없는 rename·formatting·warning 정리를 하지 않음.

원칙 우선순위:

```text
Architecture Invariants
→ Ownership / Source of Truth
→ YAGNI
→ KISS
→ SoC
→ DRY
→ SOLID
```
