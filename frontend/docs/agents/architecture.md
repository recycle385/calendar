# Architecture

## Architecture Preflight

새 상태·모델·API·이벤트·의존 관계를 추가하기 전 확인함.

1. 해당 사실과 행동을 소유하는 도메인이 어디인지 확인함.
2. 같은 사실을 관리하는 기존 원본이 있는지 확인함.
3. 새 모델이 기존 모델과 목적까지 같은 중복인지 확인함.
4. 의존 방향과 순환 참조 여부를 확인함.
5. 실제 생산자와 소비자가 있는지 확인함.
6. 같은 예외 처리가 여러 곳에 퍼지는지 확인함.
7. 한 모듈에 서로 무관한 책임을 추가하는지 확인함.

동일한 사실을 독립적으로 갱신하는 원본이 두 개 생기거나 역방향 의존이 필요하면 기존 책임 배치와 연결 방식을 먼저 재검토함. 이를 이유로 자동으로 사용자 승인을 요구하지 않음.

## 허용되는 분리

- 새로운 기능에 필요한 상태와 모델 추가는 허용함.
- 서버에서 확인한 값과 저장 전 폼·투표 편집본은 서로 다른 상태임.
- API DTO와 UI 모델은 표현 목적이 다르면 분리할 수 있음. 변환 위치와 갱신 책임을 명시함.
- 합계·정렬 결과처럼 원본에서 계산 가능한 값은 별도 원본으로 저장하지 않음.
- 같은 개념을 같은 목적의 여러 store·service에서 각각 관리하는 중복을 금지함.

## Architecture Ratchet

기존 부채 전체를 해결할 필요는 없음. 이번 변경으로 동일 개념의 원본 중복, 순환·역방향 의존, 사용하지 않는 상태·이벤트, 분산된 예외 처리, 무관한 책임 결합을 늘리지 않음.

파일·모델·상태의 총개수를 제한하는 규칙이 아님. 기존 부채 사용과 새 중복 도입을 구분함.
